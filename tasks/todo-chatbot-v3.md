## 一、硬数据（Firestore 实查，不是估计）

| 指标 | 数字 |
|---|---|
| `waOrderDrafts` 集合（bot 生成的订单草稿） | **0** |

结论：v2 已 Active，但**下单闭环一次都没跑通过**。不是「转化低」，是字面意义的零。
而生意的 61% 是「WhatsApp 聊完 → 老板手动开单」——bot 该接的活一点没接。

## 二、为什么不成交（代码级诊断）

v2 = 61 节点单体 workflow。新客从「hi」到付款要走 **6 个回合、2 次人工介入、全程打字**：

| # | 病灶 | 证据 | 后果 |
|---|---|---|---|
| 1 | 下单靠 AI 自由文本组单，客户必须一次说清 **菜+份数+午/晚+日期+地址+称呼** 6 样 | `AI Agent` systemMessage「第1步 收集四样」 | 漏一样多一轮，每轮都是流失点 |
| 2 | **零按钮**，WhatsApp interactive message 一个没用 | 13 个 whatsApp 节点全是 `operation:send` + text/image | 全靠客户打字 |
| 3 | **客户沉默后 bot 什么都不做** | 全图无 cron / 无 wait-and-followup 分支 | ← 老板「每次都要手动跟进」的根因 |
| 4 | **FIRST5 RM5 新客码从未被提及** | systemMessage 全文无 promo code | 最强钩子白扔 |
| 5 | **中文单语**，客流是中英混 | prompt 全中文、无语言分支 | 英文新客直接流失 |
| 6 | 付款必须老板人工核截图回「1」 | `Get Pending Draft`→`Image Forward`→`WA Confirm Order` | 客户付完还要等 |
| 7 | 首次回复要等 10s 防抖 + 4 个外部读（Sheet×3 + API×2）才开口 | `Wait 防抖` 10s → `Context Builder` | 新客第一印象是「已读不回」 |
| 8 | 61 节点单体，任何改动都要动整张图 | — | 无法迭代 |

**非 bot 但更致命的结构性约束**：6 点截单 ⇒ 早 6 点后进来的新客最早只能订明天。
广告中午引来的人，得到的答案是「明天送」。老板决定**此刻不改**，那 bot 必须把
「今晚下单 → 明午送达」写成卖点（抢预定 / 明天中午准时到），而不是道歉。

## 四、重做设计

### 核心原则
> **成交路径确定性化（不交给 AI），AI 只负责回答开放问题。**

现在的错误是让 LLM 当收银员。LLM 该当的是导购，收银交给写死的剧本 + 网站。

### 4.1 新客剧本（最高优先级，秒回，不经 AI）

客户第一条消息 → 200ms 内回一条把「决策所需信息」一次给全：

```
碗妈的厨房 🍲 明天 8月17日（周一）可点：
· 纳豆月见海苔饭 RM19.90
· 马铃薯炖花肉片 RM21.90
· 周一特餐：山药云耳海陆双鲜炒 RM22.90

🎁 新朋友第一单立减 RM5
👇 30 秒下单（送 Pearl Suria 一带）
https://incredibowl.my/o?ref=wa

截单：每天早上 6 点（今晚订，明天中午就到）
```

- 一条消息 = 菜 + 价 + 优惠 + 下单入口 + 配送范围 + 截单，客户不用再问
- **不防抖、不查 Sheet、不经 Gemini** —— 菜单来自 `/api/n8n/menu`（已有，可缓存）
- 英文客户发英文版 + `/en/o` 链接
- 用 WhatsApp interactive `cta_url` 按钮渲染成「立即下单」按钮；账号不支持时自动降级成纯链接
- 之后的自由提问才进 AI（Gemini + `check_delivery_fee` 工具，prompt 大幅瘦身）

### 4.2 老客剧本（found=true）

```
李太！👋 还是老样子吗？
家乡白萝卜焖花肉 ×1，午餐，送 Pearl Suria A-12-3

点这里 30 秒付好 👉 https://incredibowl.my/o?d=30&q=1&meal=lunch&ref=wa
或回「1」，碗妈发 QR 给你
```

- 上次点什么 / 常用地址 全部来自已有的 `/api/n8n/customer`
- 回「1」→ 走现有 draft → QR → 截图 → 老板回「1」链路（老板要求先看到钱，不改）
- 点链接 → FPX 秒付秒确认，老板零介入（同样满足「先看到钱」）

### 4.3 自动追单（24h 窗口内，免费）

Firestore 新集合 `waLeads` 做状态机，n8n cron 每 15 分钟扫一次：

| 时点 | 动作 | 条件 |
|---|---|---|
| T+35 min | 第一次 nudge：「刚才那几道还在哦，要碗妈直接帮你落单吗？回 1 就行」+ 链接 | 未点链接、未下单；落在 22:00–08:59 则顺延到当天 09:00 |
| **当晚 21:00** | 第二次 nudge：「今晚订，明天中午准时到 🍲」+ 链接 | 未下单、仍在 24h 窗口内 |
| 任意时点 | 客户下单 / 明确说不要 → `closed`，停止一切 nudge | — |

- ⛔ **老板明确否决 05:15 那一档 —— 太早，扰民。第二次 nudge 只能 21:00。**
- 若 nudge1 与 21:00 间隔不足 3 小时（客户傍晚才来），nudge2 顺延到次日 21:00；
  届时若已超出 24h 窗口则直接放弃（不为了发一条去买 template）
- 每个 lead 最多 2 次 nudge，绝不骚扰
- 21:00 本身是好时点：此刻下单必然是次日餐，正好对上「今晚订，明午到」的话术
- 全部落在客户最后消息后 24 小时内 → **零 template、零额外费用**
- 这条直接解决老板「每次都要手动跟进」

### 4.4 架构：61 节点单体 → 5 个 workflow

| Workflow | 职责 | 来源 |
|---|---|---|
| WF1 · Inbound | webhook、去重、分类、写 lead 状态、分派 | 重写（薄） |
| WF2 · Sales | 新客剧本 / 老客剧本 / AI 兜底问答 | 重写 |
| WF3 · Follow-up | cron 每 15 min，扫 `waLeads` 发 nudge | 新建 |
| WF4 · Boss Ops | 图片转发、求救双通道、老板转达、回「1」建单 | **从 v2 原样搬**（这几块是好的） |
| WF5 · Error | 挂了 Telegram 报警 | v2 已有，保留 |

拆开之后：改销售话术不碰订单确认，改追单不碰客服。

### 4.6 团餐 / Catering 模块（老板 2026-08-16 追加，价值最高的一块）

#### 为什么值得单独做

真实数据（Firestore 实查，近 3 个月 ≥8 份或 ≥RM150 的单）：

| 日期 | 份数 | 金额 | 每人 | 运费 | 客户 | 菜色结构 |
|---|---|---|---|---|---|---|
| 05-26 | 36 | RM612.00 | 17.00 | 免 | Chloe | 2 道（13+23） |
| 05-27 | 37 | RM666.00 | 18.00 | 免 | Chloe | 3 道 |
| 07-10 | 32 | RM606.00 | 18.94 | 免 | Abbie Tan | 2 道（22+10） |
| 07-12 | 31 | RM680.90 | 21.96 | 免 | Abbie Tan | 2 道（16+15） |
| 08-21 | 32 | RM636.80 | 19.28 | RM20 | Sasha Chin | 1 道（×32） |

- **单均 RM636 = 普通单的 30 倍**。3 个月 5 笔 ≈ RM2,800。每月多成 1 单 = +RM600。
- 菜色结构固定：当周菜单挑 **1–3 道**按人数拆，不需要设计宴会菜单。
- v2 遇到团餐只会回 `[求救老板]` —— 等于没有 bot。

⚠️ 数据缺陷（顺带发现）：手动单的 `createdAt` 被写成「配送日中午」，
所以**无法从库里算出团餐真实提前期**，也做不了手动单的 cohort 分析。不影响本方案，但值得单独修。

#### 业务规则（老板 2026-08-16 定稿，bot 照此执行）

| 项 | 规则 |
|---|---|
| 报价 | **当周菜单原价 × 份数，不打折** ← 所以 bot 能当场报价，不用求救 |
| 最低人数 | 无硬门槛，看档期 |
| 提前期 | 无硬性天数，看档期 |
| 产能上限 | **50 份/天（含散客）** |
| 菜色 | 从当周菜单选 1–3 道，按人数拆 |
| 运费 | **复用现有分档规则，零新代码**：0–7.5 km 有免运门槛（RM20/30/45）→ 团餐必然免运；7.5–25 km 固定 RM15/20/25/30 且**永不免运**；>25 km 不送。这正是老板说的「远的才收，近的免」，也与历史 5 单完全吻合 |
| 付款 | **50% 定金 + 送达前付清余额** |
| 餐具 | ✅ 附一次性餐具 |
| 送达时段 | ✅ **客户指定几点就几点（±15 分钟）** ← 会议餐最强卖点 |
| 公司收据 | ✅ 能开（⚠️ 未注册 SST，单据**绝不能有税行**） |
| 周末 / 公假 | ✅ 能做，**20 份以上才接**；不够就引导改平日 |
| 素食 / 清真 / 忌口 | ❌ 全都不做。**不主动提，客户问了才诚实告知** |

#### bot 的团餐剧本

**意图识别**（关键词命中即走团餐分支，不进普通销售剧本）：
公司 / 办公室 / 团餐 / 到会 / 包餐 / 开会 / 活动 / 聚会 / catering / office / meeting / event / pax / 几十份 / 数量 ≥ 10

① 哪天、几点要送到
② 几位

送达时间你指定几点就几点（±15 分钟内到）

`已订 + 本单 > 50` → **不当场承诺**，改口「这天档期比较满，碗妈碰一下马上回你」并推工单。

**团餐追单**：决策周期长（客户要跟 HR / 老板汇报），24h 窗口往往不够。

### 4.5 网站侧新增

1. **`/o` 极简下单页**（+ `/en/o`）
   一屏搞定：菜图+价 → 数量 → 午/晚 → 地址 → 付款。无导航、无其他菜干扰。
   URL 参数预填：`?d=<dishId>&q=<qty>&meal=lunch|dinner&promo=FIRST5&ref=wa&lead=<id>`
   无参数时 = 当日可点菜列表（新客通用入口）。
2. **`/api/n8n/lead`** —— lead 状态机（`upsert` / `list-due` / `close`），给 WF1 和 WF3 用。
3. **`/api/n8n/menu` 增补 `order_links`** —— 每道菜直接给出预填链接，bot 不用自己拼 URL。
3b. **`/api/n8n/capacity?date=YYYY-MM-DD`** —— 团餐档期自查：返回该日已订份数、
   剩余产能（上限 50）、是否周末/公假。让 bot 秒答「8月20号还能接 22 份」，
   这就是老板说的「看档期」，不用人肉算。
4. **归因**：`ref=wa` + `lead=<id>` 落进订单，两周后能拿出真实漏斗
   「bot 触达 N 人 → 点链接 M 人 → 成交 K 单」。

## 六、诚实的风险清单

- **客户到底点不点链接** —— 这是整个方案最大的未验证假设。已用「30 分钟后自动降级回
  WhatsApp 内 QR」兜底，两周后用真实点击率验证。
- **6 点截单**没改，中午来的广告新客仍然只能订明天。bot 能改善话术，改善不了物理。
- **FIRST5 剩 42 次**。按老板决定不提额度；bot 侧加保护，额度将满时话术自动去掉 RM5。
- **老板仍需人工核 QR 截图**（老板要求先看到钱）。只有走链接 FPX 的单能真正无人值守。
- **interactive 按钮**若该 WABA 未开放，自动降级纯链接 —— 不会挂，但转化打折。
- **团餐产能 50 份/天是含散客的**。日均已 ~33 碗，一单 32 份团餐就会顶到 65 —— 所以
  `/api/n8n/capacity` 不是锦上添花，是**防止 bot 接下你做不了的单**的安全阀。超限一律不当场
  承诺、只推工单给老板。
- **「±15 分钟准点送达」是最强卖点也是最硬的承诺**。bot 一旦说出口就必须做到，
  配送批次排线要把团餐当硬时间窗处理。这条要在真机 smoke 里专门验一次。
- **团餐决策周期 > 24h**，当晚 21:00 那一跟往往不够。T+2 天跟进要等 utility template
  批下来 —— 这是全案唯一的 template 依赖，排在第二阶段。
- **素食/清真答不了**这件事没有技术解。bot 只能按老板定的口径：不主动提、被问就诚实讲。
  预期会因此丢掉一部分公司团餐客户，这是知情的取舍。

## 七、复盘（2026-08-16 实施完成）

### 与计划的三处偏离（都是实施中发现更好的做法）

1. **workflow 从 5 个变 3 个**。计划说拆 WF1–WF5，实际做成
   `v3-main`（webhook 全链路）+ `v3-followup`（cron）+ `v3-error`。
   原因：同一个 webhook 的分支拆成多 workflow 必须走 Execute Sub-workflow，
   每一跳都是新的失败面，而老板还要多导入两个文件。真正该拆的是「按触发方式拆」
   —— 追单是 cron 触发，天然独立；inbound 各支线共享一个 webhook，硬拆是自找麻烦。
   v3-main 用**脚本从 v2 程序化搬运**已验证的支线（图片核款/求救转达/老板确认/定位），
   只替换销售路径，比手抄 60 个节点安全一个数量级。
2. **节点数 61 → 65，不降反升**。诚实说明：删掉了 Google Sheet 防抖五件套
   （Buffer Append/Wait/Read/Gate/Mark）和 Pin Buffer Note，但新增了整条确定性
   首触路径（Lead Touch / IF 新对话 / 双 Get / Greeting Builder / Send Greeting）、
   lead 防抖三件套、团餐档期工具、Telegram 抄送。**复杂度是从「隐式」搬到「显式」**：
   以前状态藏在 AI memory buffer + Google Sheet 里没法查，现在在 Firestore 里可查可测。
3. **防抖不再用 Google Sheet**，改用 lead 文档的 `lastMsgMs` 当水位线。
   副作用：老板**不再需要 `wa_buffer` 表**，部署少一步。

### 实施中发现并修掉的 5 个真 bug

| # | 问题 | 影响 | 位置 |
|---|---|---|---|
| 1 | **手动单 userId 用本地号码格式**（`manual_0125230066`），而 WhatsApp 传国际格式（`60125230066`） | **266 笔手动单客户对 bot 完全隐形** —— 「老客一键复购」会对几乎所有纯 WhatsApp 老客退化成陌生人接待 | `api/n8n/customer` |
| 2 | Wait 节点漏写 `unit: 'seconds'` | n8n 默认不按秒算 → **客户等 8 小时才收到回复**，且零报错 | `build-n8n-v3.mjs` |
| 3 | `/o` 预填是追加不是替换 | bot 先后发两条不同链接时，**客户会不知不觉付两单的钱**；还会看到上次残留的菜 | `QuickOrderClient` |
| 4 | `/o` 的 `<Image>` 没有 `startsWith('/')` 守卫 | 仓库允许 emoji 当占位图（新菜没拍照时），直接打成 `/_next/image?url=🍖` → 400 | `QuickOrderClient` |
| 5 | 英文侧硬编码「Orders close 6:00 AM daily」 | **周末的英文客户被告知截单时间，却不知道要等到周一** | `api/n8n/menu` |

另修：`/o`、`/en/o` 漏进 sitemap（noindex 页进 sitemap 会被 Search Console 报错）；
多日复购链接页头只显示第一项日期（客户以为一起送，实际会拆成两天）。
